# Backends plan: Metal, then D3D12

The user's ask (2026-11-13): prove rhi's abstraction of the graphics api with a second backend for real. A null backend was ruled out on 2026-11-10 ("serves no purpose"), a cpu backend (a non-conformant lavapipe) and OpenGL (macOS stops at 4.1, without compute shaders, and its implicit model would turn rhi's barriers, timelines and queues into no-ops) were weighed and set aside. Metal comes first: an explicit api unlike Vulkan, the platform the client is developed on, and one where every feature the renderer uses is known to map (KosmicKrisp runs the renderer over Metal), so its frames and times compare against KosmicKrisp's on the same machine. D3D12 was investigated alongside (below). This file holds what the shaders and rhi need of each, the decisions, the plan and its progress.

## The shaders on slang's Metal and HLSL targets (2026-11-13)

Every layout the client loads (gfx::SceneShaderLayouts with and without the device's ray queries, the ImGui renderer's, the environment filter's: 172 entry points, as `tools/shaderprecompile.cpp` compiles them) went through slang 2026.22's `slangc` one entry point at a time, with the client's options (`-O3`, column major matrices, `SHADERTYPES_H_GPU_TARGET`). The Metal output was compiled by Metal's own runtime compiler (`MTLDevice newLibraryWithSource`, MSL 3.2, the M4 Pro), as a Metal backend would compile it: Xcode's offline compiler needs the Metal Toolchain component, which isn't installed. The HLSL was emitted for shader model 6.6; DXIL needs DXC (`dxcompiler`), which slang loads and macOS doesn't have, so its validation waits for Windows.

- **The binding model** (the one large item, shared by Metal and D3D12): the shaders declare 91 resources as globals with `[[vk::binding(binding, set)]]` in 8 descriptor sets (`bindings.slang`). Slang gives globals direct Metal argument slots, and Metal has 31 buffers and 128 textures a stage, and no arrays of buffers as direct arguments (the per frame `StructuredBuffer<T> g[SHADER_TYPES_FRAME_COUNT]`): 12 of 168 entry points compiled, every error of those three kinds. In HLSL slang packed all 8 sets into one register space. The portable form is a `ParameterBlock<T>` per set: a descriptor set on Vulkan, an argument buffer on Metal, a descriptor table in its own register space on D3D12 (`-parameter-blocks-use-register-spaces`). Checked on a test file with the renderer's kinds of resources (per frame buffer arrays, the 1024 textures indexed non-uniformly, samplers, storage image arrays, push constants, the specialization constant): its compute, vertex and fragment stages pass Metal's compiler, and its SPIR-V keeps each block's set number with the fields bound 0, 1, 2... in declaration order. gfx binds by the shaders' names (`Pipeline::SetDescriptorData("gVertexBuffer", ...)`, about 200 calls): the blocks' fields keep today's names and the reflection drops the block's prefix, so those calls stay.
- **A slang crash**: its Metal target segfaults on a vertex output holding a nested struct of three or more fields without semantics (two fields compile; HLSL and SPIR-V compile it). `VertexMain` meets it through `VertexOutput.vertex`. Minimal repro: `struct T { float a; float b; float c; }; struct O { T v; float4 hPos : SV_Position; };` returned from a vertex entry point, `slangc -target metal`. A semantic on the nested member, or on each of its fields, avoids it. The cause and a fix (2026-11-13, for the user to submit to shader-slang/slang): the varying legalization flattens the struct, then matched the flattened fields to the original struct's field layouts by index, past their end for three fields, to the wrong ones for fewer (a field could lose its semantic and be dropped, and the stages' names differ).
- **`WavePrefixCountBits`** isn't in slang's Metal target (`ComputeGiVoxelize`, twice in `gi.slang`). `WavePrefixCountBits(true)` counts the active lanes below, which is `WavePrefixSum(1u)`: `simd_prefix_exclusive_sum` on Metal, an exclusive subgroup add on SPIR-V and HLSL.
- **The specialization constant** (`kSkippedLayers`, `[vk::constant_id(0)]`) becomes a Metal function constant (`[[function_constant(0)]]`), set at pipeline creation as Vulkan's is. D3D12 has none: slang makes it an ordinary shader parameter, so there it is a compile time define (a variant per value) or a root constant.
- **Ray queries** come out as `metal::raytracing` intersection queries (16 entry points), to validate once the bindings compile. Apple's bug that restarts the gpu (Metal ray tracing beside other gpu work, see docs/notes/indirect-lighting.md) is Metal's own (`rtrepro` reproduces it in pure Metal), so on a Metal backend ray queries stay opt in on macOS as they are on KosmicKrisp.
- **HLSL**: all 172 entry points compile to HLSL source at shader model 6.6.

No other kind of error showed: once the bindings are parameter blocks, the Metal check is run again over every entry point (a step of the plan below).

The check is `scripts/shadercheck.ps1 -Preset <preset> -Target metal -Validate` (or `-Target hlsl`), about a minute and a half: each layout's entry points from slang's reflection of the file (its `[shader]` functions; a regex, since slang's json of the main layout has an invalid escape), each compiled alone with the client's options, and with `-Validate` the MSL through Metal's runtime compiler (`src/tools/macos/mslcheck.mm`, which the script builds). Alone, as the backend will compile them: a whole file in one Metal library fails Metal's compiler, slang making `groupshared` memory module scope `threadgroup` variables, which a vertex function can't have. Run it after a shader change until the Metal backend compiles the shaders itself (step 4).

## What rhi asks of a backend

rhi is about 13,500 lines: 30 public headers in rhi's own vocabulary (`rhi/vocabulary.h`: formats, layouts, stages, access, descriptor types, ...) and their Vulkan implementation (`rhi/vulkan`, 33 files). The build picks the backend (`rhi::kGraphicsApi`, `rhi/rhi.h`; `RHI_SOURCE_FILES`); the class templates take it as `G`, and `BackendTypes<G>` (`rhi/types.h`, Vulkan's in `rhi/vulkan/types.inl`) names the backend's types. Of its 89 aliases, gfx and the client use only handles (`CommandBufferHandle`, `ImageViewHandle`, `SemaphoreHandle`, `PipelineLayoutHandle`, `AccelerationStructureHandle`) and `DescriptorType` and `Flags`; the rest are Vulkan structs kept as members of rhi's classes (the feature chains `PhysicalDeviceFeatures11Ex` to `14Ex`, the pipeline create infos, `DescriptorUpdateTemplateEntry`, `RenderPassBeginInfo`, ...). So gfx needs nothing of a second backend; rhi's class templates do: each backend's `BackendTypes` with types of the same roles, or members moved behind the backend's own state where the roles don't map. That is the abstraction the second backend proves or corrects.

What the renderer uses, which a backend must provide or have an exception for: Vulkan 1.4 with dynamic rendering, synchronization2, timeline semaphores, push descriptors (with update templates), push constants (at most 128 bytes, `renderer.cpp`), one specialization constant, descriptor sets from pools (8 sets, the 1024 textures indexed non-uniformly, 64 samplers), indirect draws with a count (`drawIndirectCount`, emulated where `DeviceLimits::drawIndirectCountEmulated`), dispatch indirect, buffer device addresses, acceleration structures and ray queries (optional, opt in on macOS), timestamp queries, a graphics and an async compute queue (with queue family ownership transfers), secondary command buffers (`ExecuteCommands`), a swapchain with present id and wait, a pipeline cache, and the crash reports' breadcrumbs and device faults.

The Metal api from C++: metal-cpp, Apple's header only C++ wrapper (the user's call, 2026-11-13). It is plain C++ calling the Objective-C runtime (`objc_msgSend`), as the platform layer already does without Objective-C (`platform/windowedapplication.cpp`'s presentation options and fullscreen, `platform/glfw.cpp`'s user defaults), so the project stays C and C++, and its handles (`MTL::Buffer*`, ...) are types gfx's translation units can name. The `CAMetalLayer` on glfw's view (`glfwGetCocoaWindow`) is set the same way. vcpkg's registry has no metal-cpp: an overlay port (`ports/metal-cpp`, Apple's github.com/apple/metal-cpp at its release tag for macOS 27.0.1, headers only, nothing built); the backend links Metal, QuartzCore and Foundation.

### The Metal backend's design (decided as it was built)

- **One command queue** to start, the compute and transfer queue types aliasing the graphics one (as Vulkan's do on a device without dedicated queues); dedicated compute and transfer queues come with step 10.
- **Command buffers** are one-shot in Metal: a pool's `Begin` makes a new one from the pool's queue (so `CommandPoolCreateDesc` names the queue, which Vulkan's ignores), `Retire` releases it. The handle (`CommandBufferHandle<kMetal>`) is the backend's own object: the `MTL::CommandBuffer`, its current encoder (one at a time, ended when the commands' kind changes), and what the pipeline bound on it, since rhi's bind calls and the encoder's commands meet only through the handle.
- **Timelines** are `MTL::SharedEvent`s. Submit encodes a signal on the last command buffer of a submission, before it is committed (rhi records the commands before it submits them); a wait on another queue's timeline goes in a command buffer committed just before the work (`encodeWait`), and one on the queue's own timeline needs nothing, the queue running in order. The host waits with `waitUntilSignaledValue`.
- **Descriptor sets are argument buffers** (tier 2): slang gives a parameter block's struct plain 8 byte fields in order (no `[[id]]`), so a set is a buffer in which binding b is at 8 × the counts of the bindings before it: a buffer's `gpuAddress`, a texture's or sampler's `gpuResourceID`. Each set, and the push constants (`setBytes`), is bound at the buffer index slang gave it, its slot (`rhi::ShaderSetLayout::slot`, `ShaderPushConstants::slot`), which the shader compiler reads from the MSL target's layout: slang numbers the buffers by the parameters' declaration order across the shader set's program, not by their sets, so environment.slang's parameter block is `[[buffer(0)]]` and its push constants `[[buffer(1)]]`, rhitest.slang's the other way round. (The first guess, set N at buffer N and the push constants at buffer 0, held for rhitest's kernel alone: the environment kernels read their push constants as their argument buffer, and drew black.) What a set references is made resident at its bind (`useResource`). No descriptor pool: an array of 16 sets is one shared storage buffer, each set's part 256 byte aligned (a constant buffer offset on every Mac), and a set is written once, at the update that takes it, as Vulkan's are; a pushed set (`CreateLayout`'s `pushDescriptorSets`) is written into the command buffer's own memory at each bind (`setBytes`, 4 KB at most). The update template is the backend's entries alone (no Metal object). Samplers are made with `supportArgumentBuffers`. A texture's entry is its view's resource id. Texel buffers, inline uniform blocks, dynamic offsets and combined image samplers (which slang splits into two fields) fail hard until they're needed.
- **Images** are textures, 2D or 3D (a volume), in private storage unless the host sees them (shared), each made viewable in other formats (`MTLTextureUsagePixelFormatView`: sRGB views, a depth stencil image's stencil, at a cost to some gpus' lossless compression). An upload copies a buffer into each level on the blit encoder; `Transition` only records the layout (Metal has none, and the resources are hazard tracked); `GenerateMips` is the blit encoder's. A view is a texture view (format, levels, swizzle). Clears and scaled blits come with the render passes (step 5), placement in a memory block with heaps. Formats Metal lacks fail hard: 24 bit color, and depth 24 stencil 8 on Apple's gpus; Metal's BC1 has the punch through alpha Vulkan's RGB variant ignores.
- **Barriers**: the resources are hazard tracked to start, so a barrier between dispatches is the compute encoder's `memoryBarrier`, and the host's reads after a wait need nothing (shared storage).
- **Render passes**: a render target's `Begin` makes a render pass descriptor (each attachment's texture, load and store actions, clear value) and opens the command buffer's render encoder, `End` closes it; a clear is a pass of its own that clears and stores. Draws set the bound render pipeline state and its depth stencil state (Metal keeps them apart), the push constants and the sets' argument buffers for both stages, then draw (the primitive type is the pipeline's: Metal's draws name it). A render pipeline state is made per variant and render target formats, as Vulkan's backend makes its pipelines: the vertex stage and the variant's fragment stage, its blend modes per attachment, the depth test reversed (greater, or greater or equal over a pre-pass's depth), what writes depth writing the stencil's first bit too. The topology class is named only for point lists: the vertex stage writes the point size whatever the topology (`VertexMain`, as Vulkan needs it for points), which Metal refuses in a pipeline of the triangle or line class but not in one of none (its default). A rect cleared inside a pass (`ClearRect`: the shadow atlas's tiles) is a draw, Metal clearing no part of an attachment: a triangle over the rect (the viewport and scissor), writing the clear value to that attachment alone (a fragment function per color slot, floats or unsigned integers, the clear value's bytes as Vulkan's union takes them; a depth stencil attachment's depth written with an always passing test and its stencil replaced), from a library and pipelines each render target makes at its first; the pass's viewport, scissor, cull mode and stencil reference set back after it from what the command buffer recorded of them. Secondary command buffers record inline, into the primary's render encoder (the begin info hands it to them). Scaled blits fail hard until they're needed.
- **The swapchain**: a `CAMetalLayer` the platform sets on the window's view (`PlatformCreateMetalLayer`, `platform/glfw.cpp`, through the Objective-C runtime), its images textures of its own (render target, storage and shader read usage, private storage), each copied into the layer's next drawable when it is presented (a blit, then `presentDrawable`, committed): a drawable's texture is no storage image, which the renderer's swapchain images are. Fifo or immediate (`displaySyncEnabled`), 2 or 3 images (`maximumDrawableCount`), the extent the layer's bounds times its scale, the images made again when it changes. Its binary semaphores are none (null handles, which Submit skips): the one queue runs in order, the present after the frame's commands. No present wait yet (`WaitPresent` says it can't).
- **Timestamps** are counter samples of the device's timestamp counter set, which Apple's gpus take only where an encoder begins or ends (`MTLCounterSamplingPointAtStageBoundary`: the M4 Pro samples at no draw, dispatch or blit boundary), in nanoseconds on the cpu's clock (`sampleTimestamps` gives both the same value, so the period is 1 and the profiler's first timestamp needs no command buffer), at most 4096 samples a counter sample buffer (32 KB). A timestamp written while recording is one of those samples: the start of the next encoder, the end of the open one if it was begun with samples (a compute or blit encoder then ended, so that the work after it is timed apart; a render pass's stays open to its End), or the end of the one just ended; an encoder begun with a timestamp pending is sampled at both ends, a pair of the pool's samples (a ring of as many pairs as queries: a timestamp takes at most one, so the ring can't overtake a query not yet read). A render pass's encoder is made at its first command, so that the frame graph's scope just inside it samples where its vertex stage starts and its fragment stage ends. A query is done once its command buffer has completed; a sample never written reads 0, which the profiler takes as implausible. The profiler is every backend's (`rhi/gpuprofiler.inl`), a backend's own its first timestamp alone.
- **Acceleration structures and ray queries** (opt in, `SPEEDO_RAY_QUERY=1`, as on KosmicKrisp: Apple's gpu restarts; where the device traces from every stage): `MTLAccelerationStructure`s built, refit (in place), compacted and copied on the command buffer's acceleration structure encoder. rhi names a build's inputs by gpu address, Metal takes a buffer and an offset: every buffer is registered by its address while it lives (`metal::FindBuffer`). A bottom level's triangles are Vulkan's (float3 positions, 32 bit indices or none, a 3x4 row major transform: `MTLMatrixLayoutRowMajor`). A top level's instances are rhi's (Vulkan's 64 bytes), converted by a kernel (MSL compiled at the first build, the device's) into Metal's indirect instance descriptors in the build's scratch memory just before the build, since they may be written on the gpu (compaction rewrites the static structure's id with a copy); the transform's rows become Metal's columns, the custom index the user id, the instance flags Metal's options (the same bits); an instance without a structure is masked out with another's in its place, so that the instances keep their indices (the shaders read `CommittedInstanceIndex`), and the count is written for an indirect instance descriptor (none active, none counted). A structure's address is its resource id, what Metal's indirect instances name it by. A top level references its bottom levels by id, which Metal neither keeps resident nor tracks hazards through, so a top level's build and every dispatch or draw whose sets hold a top level declare the live bottom levels used (`useResources`; a residency set later, step 10), and a barrier after builds ends the encoder, so that hazard tracking orders what follows after them. Compacted sizes go into a query pool's shared buffer, 8 bytes a query.
- **Command buffer errors**: each command buffer is made with its encoders' execution status and reports a failure as it completes (the error, and each encoder faulted or affected); its signals don't run, so what waits for them hangs, and the client's hang check reports it then.
- **The graphics api, chosen at run time** (step 9): every build has a client of each graphics api the platform has, gfx and the client compiled once per api in inline namespaces of their own (`gfx::vk`, `gfx::metal`; `gfx::kGraphicsApi` and `gfx::kShaderFormat` a copy's, `gfx/graphicsapi.h`), and the executable's C api runs the one `SPEEDO_GRAPHICS_API` names (`client/capi.cpp`: `vulkan` by default, `metal`); docs/notes/build.md has the build's side. Until then a preset (`<triplet>-metal`, a cache variable). The RHI's surface is the backend's own (Vulkan's made from the window in its devices' setup, Metal's the layer), no longer `RHIInitializationData`'s.
- **Clip space**: rhi's is Vulkan's (y down), Metal's y up: the shaders are the same, and the backend's viewport is flipped (its origin at the bottom, a negative height, as MoltenVK flips Vulkan's), which leaves the windings as Vulkan's (rhitest's culled triangle is the same one).
- **Push constants** are padded with zeros to a multiple of 16 bytes: `setBytes` must cover the whole struct the function reads, which MSL rounds up to its alignment, where Vulkan takes fewer bytes than the range.
- **Shaders**: MSL, an entry point a library (a whole file in one fails, see the check above), compiled with `newLibraryWithSource` when the layout is made (MSL 3.2, fast math, as `scripts/shadercheck.ps1` checks them); `rhi::ShaderFormat::kMsl`, the format a backend's (`kShaderFormat` is one build's today). A compute pipeline state is made from its entry point's function with the variant's specialization as function constant 0 (slang's `[vk::constant_id(0)]`), set only where it isn't 0, as Vulkan's backend does. A pipeline layout has no Metal object: its handle is the backend's (the push constants' size).

Needs: `directx-headers` (in vcpkg, the mesa port's dependency already), `directx-dxc`, `d3d12-memory-allocator`, and for enhanced barriers on older Windows the Agility SDK (not in vcpkg's registry: an overlay port, or Windows 11 24H2's runtime as the minimum). Nothing blocks it; it follows Metal, and the binding work below serves both.

## Exceptions, by "portable by default"

Each named in rhi for what the platform lacks, as `drawIndirectCountEmulated` is: Metal has no indirect draws with a count (the existing exception), timestamps only at encoder boundaries, no secondary command buffers (parallel encoding instead) and its own acceleration structure instance layout; D3D12 has no specialization constants and no push descriptors for images. None blocks: no feature the renderer needs is missing on either.

## The plan (Metal)

1. Portable shader fixes, checked on Vulkan: `WavePrefixSum(1u)` for `WavePrefixCountBits(true)`; a semantic on `VertexOutput.vertex` for slang's crash.
2. Parameter blocks, one per descriptor set, in every layout's shaders; the reflection names a block's fields as today's globals. Vulkan's sets and bindings unchanged (quick tier, visual checks); then the Metal check over every entry point again, and the HLSL one with `-parameter-blocks-use-register-spaces`.
3. The backend beside Vulkan on macOS: metal-cpp's overlay port, `kMetal` and `BackendTypes<kMetal>`, rhi's classes instantiated with them (the null backend's compile time proof), and a test over rhi generic in the backend (a compute dispatch filling a buffer), run on Vulkan as the reference and on Metal as its functions arrive. The build option that moves the client to Metal comes with step 8, when the backend has what the client uses.
4. Device, queues and timelines, buffers and images, shaders (MSL compiled at run time), compute pipelines and argument buffers: the environment filter's dispatches.
5. Render pipelines and passes, the headless output: a captured frame, compared with KosmicKrisp's (`imagecompare`).
6. The swapchain (`CAMetalLayer`), present modes, the ImGui renderer.
7. Acceleration structures and ray queries (opt in), timestamps, crash reports, residency sets.
8. The quick tier and the visual checks on Metal; frame times against KosmicKrisp's.
9. Both backends in one binary, chosen at run time (the user's call, 2026-11-13): no build variant per graphics api (the `<triplet>-metal` preset goes, and with it the CI to-do's metal build: CI runs the profile build's client on each backend instead), and a way open to switching backends inside the application later. rhi has both already (templated on `GraphicsApi`); gfx and the client name one, `rhi::kGraphicsApi` through `gfx/gpu.h`'s aliases. The way recommended: gfx and the client compiled once per backend the platform has, each copy in an inline namespace of its own (`gfx::vk`, `gfx::metal`, `client::...`, by a define per CMake object library), so that each stays monomorphic (no virtual calls, no templates through gfx) and their symbols don't clash; `main` picks one by a run time option (`SPEEDO_GRAPHICS_API=vulkan|metal`, and a command line flag; the platform's default otherwise: Vulkan, Metal on macOS once it passes what Vulkan does) and creates its application. What can't be compiled twice moves below: `kGraphicsApi` and `kShaderFormat` out of rhi's headers (a backend's shader format by its `G`), the shader loader's format the chosen backend's, core and platform once (their globals shared: `core::gApplication`, imgui's context). Installs ship precompiled shaders of both formats (shaderprecompile and the packages compile each). The cost: gfx and the client compiled twice on macOS (a clean build's extra minutes, to measure) and a larger executable; Windows and Linux compile Vulkan's alone until D3D12. Switching inside the application, later: the running application shut down (`WindowedApplication::Shutdown`) and the other backend's started on the same window (the platform's window outlives them; the Vulkan surface or the Metal layer is the backend's, released with it), the scene loaded again. A switch that keeps the scene loaded would need gfx above the backends (templated on `G` or virtual), not planned. Weighed and not chosen: gfx's classes as templates on `G` (the same doubled compile, and a rewrite of gfx into headers or explicit instantiations); a virtual rhi (a rewrite of rhi and its callers, a virtual call per command).
10.
